# Runtime cache isolation, file integrity & repair

Shipped in **game v0.17.0 / launcher v0.17.0** (PR #79). Covers three related
capabilities and the cross-package contract that ties them together:

1. A build-time **`files.json` integrity manifest** shipped inside every game archive.
2. The launcher's **Verify File Integrity / Repair / Reset Runtime Cache** toolkit
   (Settings → Game Channel Management).
3. **Per-channel `.NET` runtime-cache isolation** so each channel's self-contained
   runtime extracts to a distinct folder.

> Scope note: this targets **corrupted / partial installs**, not the AV-quarantine
> "missing runtime DLL" crash (see [Reset Runtime Cache](#4-reset-runtime-cache-windows-only)
> and `docs/planning/known-bugs.md`). The real fix for that remains code-signing.

---

## 1. The `files.json` integrity manifest (build time, CI)

Generated by `release-client.yml` (the "Generate per-file integrity manifests"
step), **after** signing and **before** packaging, for each platform's export tree.
It records every shipped file's size + sha256 so the launcher can detect missing or
corrupted files post-install.

Schema (`files.json`, schema **1** — `installer.rs::FILES_MANIFEST_SCHEMA`):

```json
{ "schema": 1,
  "files": {
    "BriskaBlast.pck": { "size": 80010556, "sha256": "<hex>" },
    "BriskaBlast.x86_64": { "size": 92160, "sha256": "<hex>" }
  } }
```

- Paths are **forward-slash, strictly relative** to the install dir. The launcher
  rejects absolute / `..` entries (`installer.rs::is_safe_relpath`).
- The generator walks the dir **last** so `files.json` never lists itself;
  `installed.json` and `saves/` are naturally absent and therefore ignored by verify.
- **Per platform:** Linux/Windows carry ~3 files (the managed DLLs are embedded
  *inside* the `.pck`); the macOS archive carries the manifest **beside** the `.app`
  (so it doesn't invalidate the ad-hoc signature) covering the bundle's full tree.

## 2. Deep Verify File Integrity (launcher)

`installer.rs::verify_install` → `verify_files`. Two passes:

1. **Cheap pass (async):** every manifest file is present and the right **size** —
   catches deleted / truncated / half-extracted files instantly, no byte reads.
2. **Deep pass:** sha256 of each survivor matches, run on `spawn_blocking` with
   chunked reads so the multi-hundred-MB `.pck` never stalls the async runtime.

Outcomes: `Ok` / `FilesMissing { count, sample }` / `FilesCorrupted { count, sample }`,
plus the legacy `ManifestMissing` / `ManifestUnreadable` / `ExecutableMissing`. When no
`files.json` is present (an install packaged before manifests existed), it falls back
to the historic exe-exists check. A future, incompatible `schema` is rejected.

Verify is a **global single-flight**: one verify at a time across all channels, and an
in-flight verify counts as "busy", disabling Verify/Repair/Uninstall (`settings.rs`,
`maintenance.rs`). The status cell shows "Verifying…" for the active channel.

## 3. Repair (launcher)

`install.rs::repair_confirmed`. Repair = **reinstall the installed version**
(fetch-by-tag via `github::release_for_version`) through the existing transactional
download pipeline (shared `stream_install` helper), then **auto re-verify**. A failed
repair leaves the prior install untouched (the staging-swap only commits on success);
saves are unaffected. The recorded `install_location` is re-validated with
`paths::install_location_collides` before any destructive work, so a hand-edited
`identity.json` can't redirect the reinstall.

It does **not** do surgical "re-download only the broken files" — GitHub Releases serves
whole archive assets, so a full reinstall is the pragmatic heal (see roadmap).

## 4. Reset Runtime Cache (Windows-only)

`maintenance.rs` + `paths.rs::clear_runtime_cache`. Deletes the game's `.NET`
runtime-extraction cache so the game rebuilds it cleanly on the next launch — for the
case where **Verify passes but the game still won't start** (a corrupt extraction).

- The cache is `%LOCALAPPDATA%\data_<basename>_windows_x86_64` (the folder Godot's
  self-contained `.NET` runtime extracts into on first launch).
- The resolved path is validated before `remove_dir_all`: it must sit under
  `%LOCALAPPDATA%` **and** exactly equal the channel's expected
  `data_<cache_basename>_windows_x86_64`.
- **It never touches antivirus.** If the problem recurs after a reset, AV is likely
  quarantining the freshly-extracted files — the user must add an AV exclusion
  themselves (the prompt says so). The durable fix for that class of crash is
  code-signing the Windows build, not this button.
- **Windows-only this ship.** Linux/macOS keep the runtime *inside* the install dir /
  `.app`, where Verify/Repair already cover it, so there's no separate cache to reset
  (and the button isn't rendered there). Activating it elsewhere is a deferred
  follow-up gated on confirming the on-disk location per platform.

## 5. Per-channel runtime-cache isolation (the build mechanism + the Godot gotcha)

**Problem:** every channel used to export with the same `.NET` assembly identity, so
all channels' runtimes extracted to the *same* `data_BriskaBlast_<platform>` folder —
a collision once more than one channel is installed.

**Fix:** give each channel a distinct identity at **export time** (in
`release-client.yml`, repo files unchanged), so the runtime extracts to a
channel-specific `data_<name>_<platform>` folder:

| Channel | `assembly_name` / cache basename | Runtime cache folder (Windows) |
|---|---|---|
| stable | `BriskaBlast` | `data_BriskaBlast_windows_x86_64` |
| ea | `BriskaBlastEA` | `data_BriskaBlastEA_windows_x86_64` |
| dev | `BriskaBlastDev` | `data_BriskaBlastDev_windows_x86_64` |

### The cross-package contract

`launcher/src/channel.rs::cache_basename()` returns exactly these strings, and the CI
bakes the same value into the game's `assembly_name`. **They must stay in lockstep** —
if one changes, the Reset Runtime Cache button looks for the wrong folder.

### ⚠️ The Godot gotcha (took 5 CI iterations to crack)

The runtime cache folder name comes from `dotnet/project/assembly_name`
(Godot source: `modules/mono/editor/.../ExportPlugin.cs` builds
`data_{CSharpProjectName}_…`; `path_utils.cpp::get_csharp_project_name()` returns
`assembly_name`). **But Godot also derives the `.sln` and `.csproj` paths from it** —
it runs `dotnet publish <assembly_name>.csproj` against `<assembly_name>.sln`. So a
per-channel rename must change **all three in lockstep**, or the C# silently fails to
compile and the `.pck` ships empty (54–236 KB instead of ~80 MB):

The CI recipe (in `release-client.yml`, all at build time):
1. `sed` `project/assembly_name` → `BriskaBlast{,EA,Dev}` in `project.godot`.
2. `mv BriskaBlast.csproj <name>.csproj` (the filename also sets the default
   `AssemblyName`, so the output DLL aligns).
3. Generate `<name>.sln` referencing `<name>.csproj`.
4. `dotnet restore <name>.sln` **explicitly** (a bare `dotnet restore` hits MSB1011 once
   the `.sln` and `.csproj` base names differ).

The export **binary name is unchanged** (`BriskaBlast.exe` / `.x86_64` / `.app`), so only
the assembly + runtime-cache folder are renamed — the launcher's install/launch path
(`find_executable`, the manifest exe) needs nothing. `RootNamespace` stays `BriskaBlast`,
so no C# namespaces change.

The macOS CI verify step is **strict + self-reporting** — it asserts
`data_<name>_macos_<arch>/<name>.dll` and lists what's present on mismatch — so a broken
rename fails the build before any release publish.

### Upgrade orphan

A machine that ran a pre-0.17.0 dev build has a `data_BriskaBlast_windows_x86_64` folder
from the old shared name. After upgrading, the dev build uses `data_BriskaBlastDev_…`,
leaving the old one as an inert ~80 MB orphan. The dev Reset button intentionally does
**not** delete it (that name is *stable's* live cache once stable exists). Manual
deletion only; an auto-cleanup gated on "no stable installed" is a deferred follow-up.
