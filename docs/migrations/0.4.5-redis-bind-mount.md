# Migration: Redis named volume → bind mount (v0.4.5)

**Applies to:** deployments running v0.4.4 or earlier that are upgrading to v0.4.5+.
**One-time per environment.** New deployments don't need this.

## What changed

`docker-compose.yml` previously mounted Redis storage from a Docker-managed named volume (`redis_data`), which lived at `/var/lib/docker/volumes/<COMPOSE_PROJECT_NAME>_redis_data/_data/` on the host. As of v0.4.5 it's a bind mount at `./redis_data/`, alongside the compose file.

Existing Redis data (admin password, runtime config, update history) **must be copied** from the old location before the new compose comes up — otherwise Redis will start with an empty data directory and the admin password will reset to the default `@admin`.

## Procedure

These commands assume your working directory is the deployment folder containing `docker-compose.yml` and `.env` (e.g. `/home/<user>/briska/dev/`).

### 1. Find the old volume's host path

```bash
PROJ=$(grep ^COMPOSE_PROJECT_NAME .env | cut -d= -f2)
sudo docker volume inspect ${PROJ}_redis_data -f '{{.Mountpoint}}'
```

Note the printed path. Typical: `/var/lib/docker/volumes/briska-dev_redis_data/_data`.

If `COMPOSE_PROJECT_NAME` isn't set in your `.env`, fall back to the directory name (whatever `docker compose ps` shows as the prefix on container names).

### 2. Stop the stack

```bash
sudo docker compose down
```

This makes sure Redis isn't actively writing while we copy.

### 3. Pull the v0.4.5 compose file

```bash
curl -fsSL -o docker-compose.yml https://raw.githubusercontent.com/Warstorm548/Briska-Blast/dev/docker-compose.yml
```

(For non-dev channels, replace `dev` in the URL with the tag or branch you're running.)

### 4. Create the bind mount directory with correct ownership

The official `redis:7-alpine` image runs as uid/gid 999. The host directory must match or Redis will fail to write the AOF.

```bash
mkdir -p redis_data
sudo chown -R 999:999 redis_data
```

### 5. Copy the existing data

Use the path from step 1:

```bash
sudo cp -a /var/lib/docker/volumes/${PROJ}_redis_data/_data/. ./redis_data/
sudo chown -R 999:999 ./redis_data
```

`cp -a` preserves permissions and timestamps. The trailing `/.` copies the directory contents (including dotfiles) rather than the directory itself.

### 6. Bring the stack up on the new mount

```bash
sudo docker compose pull
sudo docker compose up -d
sudo docker compose ps
sudo docker compose logs redis --tail 20
```

Look for these in the Redis logs:
- `Loading AOF appendonly.aof` (or `Loading AOF appendonly.aof.X.base.rdb` on newer Redis layouts)
- `DB loaded from append-only file`
- `Ready to accept connections`

If Redis logs `Permission denied` or `Read-only file system`, recheck step 4 — ownership must be uid 999.

### 7. Verify application state

Visit `https://<your-host>/admin` and log in **with the password you previously set** — not the default `@admin`. If `@admin` succeeds, Redis started with an empty data directory, which means the copy in step 5 went wrong. Roll back (see below) and re-run.

Also confirm runtime config survived:
- `MIN_LAUNCHER_VERSION` / `MIN_GAME_VERSION` show your previously-set values.
- Server Updates panel still shows your prior check history.

### 8. Leave the old volume in place (rollback safety net)

Do **not** delete `${PROJ}_redis_data` yet. After a few days of confidence on the new mount, you can reclaim the disk space:

```bash
sudo docker volume rm ${PROJ}_redis_data
```

## Rollback

If verification in step 7 fails or Redis won't start:

```bash
sudo docker compose down
git -C /tmp/briska clone https://github.com/Warstorm548/Briska-Blast.git --depth 1 --branch v0.4.4-dev.1
cp /tmp/briska/Briska-Blast/docker-compose.yml ./docker-compose.yml
sudo docker compose up -d
```

Because the old volume was left intact in step 8, the previous compose file references it and brings Redis back up with the original data unchanged. You can then troubleshoot the bind-mount migration without pressure.

## Per-environment notes

If you run multiple environments on the same host (prod / staging / dev each in their own directory), repeat steps 1–7 inside each directory. The bind mount `./redis_data/` is relative to the compose file, so each environment isolates by directory location — there's no cross-env contention.
